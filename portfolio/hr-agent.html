HR Agent Agentic Recruiting Assistant

An agentic HR assistant that ingests candidate resumes, scores them against the job description, answers recruiter questions over a vector store, drafts shortlisting emails, and schedules interviews — all from one chat interface.

View on GitHub

01 · Problem

Problem Statement

The Challenge

Recruiters manually screen every resume, hunt for candidate details, and juggle shortlisting emails and interview scheduling across tools. Resumes full of personal data also flow into LLMs unredacted, which is a privacy risk.

Why It Matters

Manual screening is slow and inconsistent, and scoring each resume against a job description by hand is error-prone. Sending raw resumes with emails, phone numbers, and addresses into an LLM exposes candidate PII unnecessarily.

Goals

  • Auto-ingest resumes and score them against the JD (ATS score out of 10).
  • Redact PII before any LLM processing.
  • Answer recruiter queries over a RAG index of candidates.
  • Draft shortlisting emails and schedule interviews, always after user confirmation.

02 · Design

System Architecture

How It Works

  1. Candidates submit a form (name, email, phone, resume PDF/DOCX); the workflow routes the file by type and extracts its text.
  2. Regex code pulls structured contact info (email, phone, LinkedIn, GitHub, name, address) and a sanitizer redacts that PII before any LLM call.
  3. The LLM scores the sanitized resume against the job description (ATS out of 10) and produces a summary and skills; the record is written to Postgres and indexed into a Supabase vector store (candidate_2).
  4. An HR chat agent uses a RAG sub-agent to pull candidate info and candidate_id, drafts shortlisting emails via a Mail sub-agent, and books meetings via a Calendar sub-agent — always confirming with the user first.

Tech Stack

  • AI / LLM — Google Gemini (chat + embeddings)
  • RAG / Vectors — Supabase pgvector (candidate_2)
  • Data — Postgres (candidates, batches)
  • Orchestration — n8n · Memory & Cache — Redis
  • Email / Calendar — Gmail draft, Google Calendar

04 · Process

Standard Operating Procedure (SOP)

The repeatable process used to build and run the HR Agent.

01

Collect Candidate Details

Recruiters capture First Name, Last Name, Email, Phone, and the resume via a web form, and a switch node routes the file by type (PDF or DOCX) to extract its text. This is the single entry point where a candidate enters the pipeline.

02

Extract & Sanitize PII

Regex code pulls structured contact data (email, phone, LinkedIn, GitHub, portfolio, name, address) out of the resume text. A sanitizer then redacts that personal information into placeholders so no PII ever reaches the LLM.

03

Score the Resume Against the JD

The job description is downloaded from Google Drive and extracted, then a Gemini agent generates an ATS score out of 10, a summary, and a skill list through a structured output parser. This turns every resume into a comparable screening record.

04

Store & Index the Candidate

The candidate row is inserted into Postgres and its candidate_id is returned, then the summary, ATS, and skills are embedded with Gemini and written to the candidate_2 vector store with batch metadata. Re-submissions update the existing vector instead of duplicating it.

05

Answer, Mail & Schedule

The HR chat agent (with Redis memory) retrieves matching candidates through the RAG sub-agent and always asks before acting. It drafts shortlisting emails with the Zoom meeting link via candidate_id, and books interviews on Google Calendar only after the user confirms.

Notes & Caveats

The vector-store lookup is scoped to the active batch so HR only sees the current hiring round. Always confirm before drafting mail or scheduling — that's enforced in the orchestrator's system prompt. The resume sanitizer is the privacy gate: keep it upstream of every LLM call.
